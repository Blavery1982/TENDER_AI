## Текущий продавец и порядок

`актуальный продавец/ИНН → проверка компании → КАД → остальные сигналы → antifraud`.
ИНН определяется по текущим юридическим страницам, оферте или счёту, а не по
первому совпадению или старому Wayback. Неоднозначность — YELLOW без поиска КАД.
Архивные ИНН отдельно проверяются только при конкретном подозрении/расхождении.

В LIVE продавец установлен, если юридическая страница прочитана, найден один
однозначный ИНН и исследованные текущие страницы не противоречат ему.
ИНН только в товарной карточке либо script/style не подтверждает продавца.
`company_checker` — адаптер реестра по тому же ИНН; без него active неизвестен.
Штатный LIVE-сбор реестра компаний ещё не подключён.

## Production-КАД

`ИНН → поиск → число дел ответчика → краткий итог`.
`suppliers/kad_client.py` использует HTTP или имеющийся Playwright-контекст;
одна попытка без смены транспорта и повторного поиска после технической ошибки.
Поиск во всех ролях не означает, что все найденные дела — иски к поставщику.
В строке выдачи наш ИНН сопоставляется с обозначенной группой участников либо
столбцом с заголовком роли. Считаются только дела, где наш ИНН — ответчик;
одновременная роль истца не отменяет роль ответчика.

Карточки, решения и документы не открываются. Если ИНН/роль не видны в выдаче,
проверка не подтверждается; нет дополнительного запроса к карточке.
Идентификаторы строк используются только в памяти для устранения дублей между
необходимыми страницами и не сохраняются после проверки.
Между страницами есть пауза, технический лимит страниц означает непроверенность,
а не критерий надёжности. Изменение счётчика и неполная выдача — ручная проверка.

После проверки сохраняются только:
`searched_inn`, `checked_at`, `technical_status`, `defendant_cases_count`,
`kad_status`, `reason`.
Никаких списков, номеров, ссылок, категорий, ролей отдельных дел или решений.

- `KAD_CHECKED`, N = 0: KAD-цвет GREEN, КАД сам по себе не создаёт предупреждения.
  Это не полный зелёный antifraud и не доказательство активности компании.
- `KAD_CHECKED`, N > 0: KAD-цвет YELLOW; «Есть судебные дела в качестве ответчика:
  N. Требуется вручную проверить судебные иски и добросовестность поставщика».
  Никакой автоматической оценки значимости/обоснованности исков или RED из КАД.
- CAPTCHA/challenge/HTTP 451/timeout/другая ошибка/неполнота/неизвестная роль:
  `KAD_REQUIRES_MANUAL_CHECK`, YELLOW, count = null, явная причина.
- Неустановленный текущий продавец: `KAD_CURRENT_SELLER_UNDETERMINED`, YELLOW.

Предыдущая диагностика получила 451; после неё LIVE не выполнялся.
Новый подсчёт в реальной выдаче пока не подтверждён. UNIT — синтетические страницы.
`kad_diagnostic` остаётся отдельным инструментом разработки, который может
читать и сохранять подробности одной карточки; его формат не является
production-результатом и не подтверждает новый production-допуск.

## Итоговый antifraud

Сохраняются профильность сайта, возраст домена, тематика истории, активность
компании, согласованность реквизитов, история юрлиц, госзакупки и прежние
предупреждения о молодом домене, новой компании, смене руководства.
Сильные риски других проверок: несовпадение компании/реквизитов, смена тематики,
одновременная оплата разным юрлицам, недействующая текущая компания.
Сохраняется их прежний алгоритм: сильный риск при минимум
`strong_risk_min_total_flags` записях риска — RED; несовпадение реквизитов
достаточно само по себе. Нет положительных признаков при непроверенности —
белый; иначе предупреждения — жёлтый. Без рисков ИНН + действует +
(реквизиты согласованы ИЛИ продавец установлен) +
(старый домен ИЛИ стабильная история) допускают зелёный при проверенном КАД.

Затем действует допуск: текущий продавец не установлен — YELLOW; текущий
продавец установлен, но КАД неизвестен/по другому ИНН — YELLOW с причиной;
N > 0 — YELLOW. Другой подтверждённый RED не понижается из-за КАД.
Это действует и для доверенного домена при установленном продавце либо явно
переданном kad_check. Старый вызов только по доверенному домену без сведений
о продавце/КАД сохраняет исходный shortcut; LIVE всегда передаёт эти сведения.

RDAP/WHOIS и Wayback CDX идут после КАД. Наличие архивных снимков не доказывает
прежнюю тематику. CMS/DNS, общий IP и физлица не заменяют проверку продавца.
Числовой порог недавней регистрации компании не задан; не назначай его сам.

## Кэш, файлы, CLI

`data/cache/kad/<ИНН>/<дата-время>.json`: schema_version=2/run_id — служебные
метаданные кэша, result — только шесть полей выше. Старый подробный schema=1
не используется, не переносится и не переоценивается как успешная проверка.
`data/suppliers/_kad/<хэш-домена>/<дата-время>.json`: только шесть полей результата.
Источники текущих реквизитов остаются отдельно в обычной проверке продавца.
Cookies/сессии не сохраняются.

По умолчанию кэш, включая технические ошибки, используется только в одном
запуске. Между запусками — только успешный результат в пределах явно заданного
`cache_max_age_hours`, по умолчанию null. Срок пользователем ещё не утверждён.
Исходная дата сохраняется. `--force-refresh` — явный ручной повтор,
не автоматическая попытка после CAPTCHA/блокировки.

```bash
.venv/bin/python -m suppliers.kad_client <актуальный_ИНН>
```

## Счёт и закупочный отбор

`verify_invoice_recipient()` сравнивает ИНН счёта с текущей компанией, не название.
Отсутствующий счёт отличается от несовпадения; LIVE автоматически его не получает.
В EXACT_MODEL экономика проверяется до antifraud; запас и скидка не являются
окончательной рентабельностью. TOP-3 исключает красных, допускает жёлтых/белых
со своими статусами, неизвестное наличие — резерв. Старый select_quotes берёт
только зелёных в пределах порога. purchase_price не заполняется публичной ценой.
Самостоятельная проверка не требует тендера, Sheets или экономического допуска.
