# Возможности TENDER_AI и подтверждение тестами

Дата анализа: 15.09.2026. Проверена текущая локальная версия, включая незакоммиченные изменения. Источники: Python-код, тесты, README и сохранённые результаты запусков. Внешние сервисы в рамках этого анализа не запускались.

## Вывод

Программа уже реализует существенную часть обработки закупки: сбор ЕАТ → фильтры → карточка и документы → извлечение требований → определение/подбор модели → публичные предложения → проверка поставщика → предварительная экономика → отчёт и Google Sheets.

Это система из нескольких рабочих сценариев с ограничениями. Подтверждения полностью автоматического массового прохода произвольных закупок через все этапы до готовности к участию нет. Запуск `main.py` без параметров печатает сообщение и завершается.

Все **694 автоматических теста в 49 файлах прошли**: ошибок, падений и пропусков нет. Это подтверждает проверяемую локальную логику и отдельные интеграции на подставных ответах; не доказывает сегодняшнюю доступность ЕАТ, магазинов, КАД или Google Sheets. Некоторые тесты действительно читают сохранённые DOC/DOCX/XLSX/PDF и запускают локальное OCR.

## Ограничения и пробелы

1. **Нет подтверждения полного массового сценария для всех типов закупок.** MVP ограничивает supplier search 10 точными позициями; позиции без модели распределяет, но сам не прогоняет через общий подбор. `second_queue.py` реализует отдельный контур. Быстрый `priority_production.run_exact_fixture()` поддерживает одну exact-model позицию. `live_e2e.run()` собирает payload из сохранённых файлов.
2. **Справка MVP расходится с кодом.** `main.py` описывает `--mvp-exact-batch` как «без Google Sheets», но `mvp_exact_batch.run()` по умолчанию получает `upsert_live_payload` и вызывает writer для каждой проанализированной позиции. Такой запуск может записывать внешнее состояние.
3. **API-лимит карточек не действует.** `eat/live_api_collection.py` принимает `detail_limit`, но не использует его. `details_requested` присваивается числу уникальных записей списка. Тесты не проверяют соблюдение этого лимита и точность метрики.
4. **Яндекс не выбран повсеместно.** `discover_models()` без переданного provider использует `WebProvider`, чей поиск обращается к Bing RSS. В контрольном запуске второй очереди Яндекс передаётся явно. Это расходится с постоянной договорённостью использовать Яндекс для товарного поиска.
5. **Проверка страниц не везде через Playwright.** Стандартный fetcher `live_price_search.py` использует `urllib`; `YandexSearchProvider` по умолчанию делегирует чтение `WebProvider`. Такие пути не выполняют JavaScript и не используют авторизованную браузерную сессию магазина. Это также расходится с договорённостью подтверждать предложения через Playwright.
6. **Проверки КАД и юрлиц не гарантируют полный автоматический аудит.** Оценка арбитража умеет обработать переданные дела и корректно сообщает об отсутствии проверки. Наличие функции и зелёный тест с fake-делами не подтверждают получение актуальных дел. Доверенные домены имеют отдельную ветку допуска по списку; статус PASSED не следует понимать как доказательство полного исследования каждого продавца маркетплейса.
7. **Прослеживаемость покрыта слабо.** В pipeline проверяется наличие результата у каждой позиции; отдельных regression-тестов на ТН ВЭД, страну, исключения и устаревание справочника в `tests/` не найдено. Актуальность правовых справочников этим анализом не проверялась.
8. **Новый магазинный вход пока подтверждён mocks.** Обнаружение штатной формы реализовано; автоматический переход к форме конкретного магазина и подтверждённый реальный вход не установлены. README прямо указывает необходимость live-проверки после настройки/CAPTCHA.
9. **Тесты зависят от локального набора данных.** Часть читает реальные сохранённые закупки и документы; перенос в чистую среду без этих файлов и macOS `textutil` отдельно не проверен. Прямых тестов полного `download_active_tenders()` и всего live MVP с внешними сервисами нет.
10. **Публичная цена остаётся ориентиром.** Код в проверенных сценариях сохраняет закупочную цену неизвестной и не подменяет неизвестную доставку нулём. Положительный предаудит не означает готовность к участию без подтверждения закупочной цены и расходов. Среди 694 тестов есть и слабые проверки отдельных словарей/полей; число тестов не заменяет покрытие рисков.
11. **Некоторые статусы payload не опираются на доказательства.** `pipeline/live_e2e.build_payload()` задаёт текст об актуальной официальной карточке производителя без проверки её наличия; текст о российском Яндекс Маркете выбирается по наличию принятых предложений, а не по конкретному источнику. `priority_production.run_exact_fixture()` исправляет статус производства на неподтверждённый, но остальные потребители общего payload могут получить слишком уверенное утверждение. Это требует regression-тестов и исправления.
12. **Документация частично устарела.** Основной README говорит о будущей работе и пустом `requirements.txt`, хотя зависимости заполнены и модули реализованы. `reports/production_preflight.md` датирован 09.09 и не описывает все последующие изменения.

Приоритет следующих проверок: привести CLI к фактическим побочным действиям; проверить API-лимит; унифицировать Яндекс/Playwright; провести ограниченный полный проход текущей версии для одной точной и одной подбираемой модели с проверкой итоговых артефактов; дополнить аудит оставшихся архивов и тесты прослеживаемости.
