# AGENTS.md — правила работы с проектом TENDER_AI

Этот файл содержит рабочий контекст и правила для Codex и других кодовых
агентов, работающих с репозиторием. Файл является живым документом: новые
договорённости с владельцем проекта нужно добавлять сюда, если они относятся
к нескольким задачам или должны соблюдаться постоянно.

## 1. Как общаться с владельцем проекта

- Основной язык общения — русский. Английские названия модулей, команд,
  переменных и API оставлять без перевода, когда так понятнее.
- Сначала сообщать результат, затем кратко объяснять, что было изменено и как
  это проверено.
- Не ограничиваться предложением плана, если задача понятна и действие
  разрешено: выполнять работу до проверяемого результата.
- Если есть несколько разумных вариантов, выбирать безопасный и минимальный
  по объёму вариант, а принятое допущение явно фиксировать в ответе.
- Задавать вопрос только тогда, когда без ответа нельзя безопасно определить
  требуемое поведение или вопрос меняет результат задачи.
- В финальном ответе указывать изменённые файлы, выполненные проверки и
  оставшиеся ограничения или `TODO`, если они есть.
- Не использовать лишнюю бюрократию и длинные формальные отчёты. Формулировки
  должны быть конкретными и понятными.
- По указанию владельца от 15.09.2026 проверки счётчика лимита Codex и
  уведомления об остатке временно отключены. Не открывать интерфейс для
  проверки лимита и не возобновлять проверки без нового указания владельца.

## 2. Что представляет собой проект

Канонический контракт правил проекта находится в
[`docs/TENDER_AI_MASTER_SPEC.md`](docs/TENDER_AI_MASTER_SPEC.md). Перед изменением
production-логики, pipeline, Sheets или regression-тестов сверяться с ним;
README должен оставаться кратким представлением этих же правил.

`TENDER_AI` — локальная Python-система для работы с тендерами и закупками.
Текущий рабочий контур включает:

- сбор и нормализацию публичных закупок ЕАТ;
- фильтрацию закупок и позиций по бизнес-правилам;
- загрузку и анализ документов закупки;
- архивирование документов конкретного тендера;
- поиск точных моделей и рыночных предложений;
- проверку поставщиков и экономический предаудит;
- расчёты и принятие решений по позициям;
- подготовку отчётов;
- интеграцию с Google Sheets;
- подключение AI-провайдеров и вспомогательные проверки безопасности.

Проект находится в активной разработке. В README и именах каталогов встречается
формулировка «будущая работа» — такие части нельзя считать полностью
завершёнными без проверки текущего кода и тестов.

## 3. Карта каталогов

- `main.py` — CLI-точка запуска.
- `eat/` — клиенты, авторизация, сессии, сбор, пагинация, нормализация и
  фильтрация данных ЕАТ.
- `filters/` — правила отбора, включая семантические запрещённые слова.
- `documents/` — извлечение текста, OCR, анализ документов, архив тендера и
  обнаружение марок/брендов.
- `model_search/` — планирование запросов, поиск и ранжирование моделей,
  проверка соответствия и поиск цен.
- `suppliers/` — реквизиты, поиск, проверка, ранжирование, арбитраж и
  экономический предаудит поставщиков.
- `calculator/` — схемы, формулы и решения по расчётам.
- `pipeline/` — оркестрация batch-, MVP-, production- и live-сценариев.
- `google_sheets/` — клиент, структура рабочей таблицы, upsert и удержание
  данных.
- `ai/` — базовые классы, маршрутизация и провайдеры AI.
- `security/` — credentials, проверки заказчика и трассируемость.
- `core_knowledge/` — только проверенные детерминированные правила проекта.
- `config/` — настройки без секретов.
- `reports/` — отчёты и подготовленные результаты.
- `data/` — локальные рабочие данные, fixtures, результаты тестов и архивы.
- `tests/` — автоматические тесты.
- `logs/` — технические журналы; каталог и логи не должны попадать в Git.
- `secrets/` — локальные секреты; каталог исключён из Git.

## 4. Правила изменения кода

- Перед редактированием читать относящиеся к задаче модули, тесты и README.
- Сохранять существующие пользовательские изменения в рабочем дереве. Не
  использовать деструктивные команды вроде `git reset --hard` или массового
  удаления файлов.
- Делать минимальные изменения, соответствующие задаче. Не проводить
  несвязанный рефакторинг и не менять публичное поведение без необходимости.
- Новую бизнес-логику размещать в соответствующем доменном модуле, а не в
  `main.py`. В `main.py` оставлять CLI-диспетчеризацию.
- Не дублировать правила фильтрации, нормализации, расчётов и допуска
  кандидатов. Сначала найти существующий источник истины.
- Для нового или изменённого проверяемого правила добавлять regression-тест.
- Если правило ещё не принято человеком, оформлять его как
  `CORE_RULE_CANDIDATE`. AI не должен самостоятельно добавлять правила в
  `core_knowledge/approved_rules.json`.
- Точные словари и сопоставления хранить в JSON, сложную проверяемую логику —
  в Python-модуле соответствующего домена.
- Не подменять live-проверки фиктивным успешным результатом. Если внешний
  сервис недоступен, явно сохранять статус ошибки, неполноты или ручной
  проверки.
- Сохранять трассируемость: результаты по возможности должны содержать источник,
  ссылку, документ, страницу или фрагмент, на котором основан вывод.

## 5. Git и GitHub

- Сообщения коммитов, описания pull request, issue и комментарии к изменениям
  на GitHub писать на русском языке.
- Комментарии в исходном коде проекта также писать на русском языке, если для

- Перед коммитом проверять diff и не включать секреты, локальные credentials,

## 6. Секреты, персональные и рабочие данные

- Не записывать пароли, токены, ключи, cookies, service-account JSON и данные
  авторизованной сессии в код, тесты, README или отчёты.
- Локальные значения хранятся в `.env` и/или `secrets/`. Ориентироваться на
  `.env.example`, который содержит только имена переменных и безопасные
  значения-заглушки.
- Не выводить секреты в терминал, логи, commit, diff или финальный ответ.
- Считать содержимое `data/`, `data/contracts/`, `data/tenders/` и выгрузок
  потенциально чувствительными рабочими данными. Не отправлять их во внешние
  сервисы без явной необходимости и разрешения в контексте задачи.
- Не менять `.env`, `secrets/` и существующие рабочие данные без явной
  необходимости для задачи. Перед массовым или необратимым изменением сначала
  сделать read-only проверку точного набора файлов.

## 7. Архив тендера и документы

Новая загрузка карточки через `eat.single_purchase` должна сохранять документы
в единый архив:

```text
data/tenders/<tender_number>/
```

Для новых закупок имя папки — номер закупки ЕАТ (`tradeNumber`, например
`200908050126100191`). UUID (`purchase_id`) сохраняется в метаданных и ссылках
API. Существующие папки не переименовывать и не переносить: повторная работа
с ранее сохранённой закупкой использует её прежнюю папку. Если номер новой
закупки не получен, не создавать папку по UUID, а сообщить о неполных данных.

В архиве ожидаются исходные документы, `tender.json`,
`document_extraction.json` и `brand_audit.json`. Старый каталог `data/contracts/`
удалён после переноса документов. `passport.md` — основной структурированный
паспорт тендера для быстрого извлечения сведений и состава файлов.

Одноразовая миграция старых документов:

```bash
.venv/bin/python -m documents.migrate_tender_archive
```

Проверка архива на марки и товарные знаки:

```bash
.venv/bin/python main.py --audit-tender-archive
```

Результаты аудита находятся в `data/tenders/_brand_lists/`:

- `brands_found.json` — марка подтверждена, указаны документ, страница и
  фрагмент;
- `brands_not_found.json` — документы прочитаны, совпадений нет;
- `review_required.json` — архив неполный, OCR завершился с ошибкой или найден
  неоднозначный кандидат.

## 8. Окружение и запуск

Проект рассчитан на локальное виртуальное окружение `.venv`. Зависимости
зафиксированы в `requirements.txt`. Основной способ запуска — через `main.py`:

```bash
.venv/bin/python main.py
```

Перед live-сценариями проверить наличие нужных локальных credentials и сессии.
Переменная `EAT_COLLECTION_BACKEND` переключает сбор ЕАТ; значение по умолчанию
— `browser`, значение `api` выбирает API-сборщик через браузерную сессию.

Основные безопасные и диагностические команды:

```bash
.venv/bin/python main.py --production-dry-run
.venv/bin/python main.py --production-dry-run --resume
.venv/bin/python main.py --eat-live-collection-audit
.venv/bin/python main.py --eat-api-smoke-test
.venv/bin/python main.py --eat-live-api-collection
.venv/bin/python main.py --model-search-test
.venv/bin/python main.py --procurement-audit-test
.venv/bin/python main.py --audit-tender-archive
```

Команды с `live`, авторизацией, Google Sheets или внешним поиском могут читать
или изменять внешнее состояние. Перед их запуском убедиться, что это входит в
текущую задачу, и ограничивать объём через доступные параметры.

## 9. Тестирование

- Для изменения доменной логики запускать связанные тесты из `tests/` и
  ближайшего доменного модуля.
- Для изменений, затрагивающих несколько этапов pipeline, запускать как
  минимум соответствующие unit/integration-тесты и проверять сформированные
  артефакты.
- Для небольшого изменения документации или локального текста достаточно
  проверить diff и отсутствие случайных изменений.
- Не считать тест успешным доказательством корректности live-интеграции, если
  он использовал только fixture или mock.
- После проверки сообщать точные команды и их результат. Если проверка не
  запускалась из-за credentials, сети или другого ограничения, указывать это
  явно.

## 10. Рабочий процесс Codex

1. Определить границы задачи и проверить состояние рабочего дерева.
2. Найти существующий код, конфигурацию, тесты и артефакты, относящиеся к
   задаче.
3. Сформулировать минимальное изменение и при необходимости зафиксировать
   допущения.
4. Внести изменение небольшими проверяемыми шагами.
5. Запустить проверки, соответствующие риску и масштабу изменения.
6. Проверить diff, не затронуты ли секреты, большие рабочие данные и чужие
   незавершённые изменения.
7. Передать результат на русском языке: что сделано, где, как проверено и что
   осталось сделать.

## 11. Постоянные договорённости проекта

- **Категория закупки** — обязательное поле production-результата с одним из
  трёх точных значений: `Закупка по модели`, `Закупка с определением модели по
  параметрам` или `Закупка товара без существующей модели`. Явное обозначение
  заказчика (модель, марка, артикул, товарный знак, серия или однозначное
  коммерческое название из разрешённого источника) даёт первую категорию.
  Товар, который обычно выбирается как конкретная модель, без явного
  обозначения получает вторую категорию и проходит подбор по требованиям.
  Массовый/оптовый товар, для которого модельный подход неприменим, получает
  третью категорию по детерминированному словарю `config/customer_product_context.json`.
  Для третьей категории подбор моделей, цены, поставщики, antifraud, КАД,
  контракт и экономика не запускаются; в итог записывается ровно
  `Алгоритм просчета не доработан`.

- `Дополнительные расходы, ₽`: production-upsert записывает числовой 0 только
  в пустую ячейку. Существующее число, включая 0, сохраняется без перезаписи.
  Обычный сбор сохраняет это поле. Непустой текст не заменять автоматически.
  Контракт анализировать только на отдельные специальные обязанности и
  кратко писать их в `РЕЗУЛЬТАТ АНАЛИЗА КОНТРАКТА`. Типовые оговорки о
  транспортных расходах, страховании, налогах и иных включённых в цену
  расходах игнорировать. Специальные условия не меняют сумму расходов.
  Формула использует число в Sheets; пустота становится явным 0 при upsert.

Этот раздел предназначен для дополнения по мере работы.

- Бизнес-решение EXACT_MODEL сохранять в итоговый JSON и human-readable отчёт,
  а статус и короткие причины выводить в существующую колонку Google Sheets
  «Текущий итог просчета и анализа» без добавления колонок. На листе
  «Тесты программы» использовать отдельный этап «Бизнес-решение».
  Обычный сбор сохраняет готовое решение, новый просчёт заменяет его.
  Не смешивать предварительный запас до расходов и итоговую рентабельность КП.
  По уточнению владельца неполная экономика → 🟡 РУЧНАЯ ПРОВЕРКА является
  принятым основным правилом без CORE_RULE_CANDIDATE. Итоговая рентабельность
  приоритетна; предварительный запас — только промежуточная справка.
  🔴 требует достаточных окончательных отрицательных данных. 🟢 требует
  полного просчёта, проходной итоговой экономики, минимум трёх подходящих
  поставщиков, подтверждённой возможности поставки, отсутствия обязательных
  antifraud-предупреждений и учёта всех известных обязательных расходов.
  В слое бизнес-решения цена подачи считается как `A × 1,18` по средней цене
  трёх подходящих КП; расходы равны `A + дополнительные расходы + комиссия ЕАТ`,
  УСН — 15% положительной налоговой базы, а чистая прибыль должна быть не ниже
  12% от `A`. Цена выше НМЦК или чистая прибыль ниже 12% при полном расчёте —
  🔴; нехватка входных данных — 🟡. Предварительный запас этот критерий не
  заменяет.

- Комиссия ЕАТ является входом закупки, а не расчётным показателем программы.
  Единственный источник — `raw.lot.commissionFee`; каноническое поле после
  нормализации — `procurement.commission_fee`. Его передавать в экономику,
  business decision и колонку Sheets «Комиссия площадки, ₽» без пересчёта.
  Отсутствие комиссии сохранять как `None/unknown` и направлять в 🟡 ручную
  проверку; не подставлять ставку, НМЦК, цену позиции или нулевое значение.

- Навык `supplier-check` в `skills/supplier-check/` содержит редактируемый
  каталог правил проверки поставщиков и поддерживает отдельную проверку по
  ИНН/сайту без тендера. Личный навык `~/.codex/skills/supplier-check` ссылается
  на эту папку. Изменение каталога навыка не меняет runtime автоматически;
  при задании изменить правила программы синхронизировать профильный Python-код,
  regression-тесты и каталог навыка. Недоступные внешние проверки сохранять
  явно, в том числе при зелёном статусе по доверенному домену.

- Проверка КАД выполняется детерминированным Python/Playwright-сборщиком по
  однозначно установленному ИНН актуального продавца. Архивные ИНН без конкретной
  причины автоматически не проверять. Неустановленный продавец — YELLOW без
  запроса КАД; CAPTCHA/защита — `KAD_REQUIRES_MANUAL_CHECK`, остановка попыток.
  Непроверенный или неполный КАД неизвестного поставщика не допускает GREEN;
  КАД считает только дела ответчика по актуальному ИНН: 0 не создаёт предупреждения,
  любое N > 0 — YELLOW для ручной проверки исков и добросовестности. Прежний
  анализ банкротства/свежести и пороги 3/2/730 отменены. Production не открывает
  карточки, решения или документы, не хранит номера, ссылки, категории и списки
  дел. Хранить только ИНН, дату, технический статус, defendant_cases_count, KAD-цвет
  и короткий reason. kad_diagnostic — только инструмент разработки.
  Срок кэша между запусками пока не утверждён;
  без заданного срока повторно использовать только внутри текущего запуска.

- **HARD ARCHITECTURE RULE: production/runtime TENDER_AI must not require Codex, ChatGPT, OpenAI API or any generative AI/LLM. AI is a development-time tool only unless the user explicitly changes this rule.**

- До определения модели/идентификатора и товарного price search детерминированно
  определять тип каждой позиции. Официальная категория ЕАТ `ТОВАРЫ/РАБОТЫ/УСЛУГИ`
  приоритетна. Поиск товара разрешён только при `position_kind == goods`;
  `works/services` блокировать, `uncertain` направлять в ручную проверку.
  Разные определённые типы позиций дают `mixed`; допуск проверять по каждой
  позиции. Модель объекта услуги/работы не является моделью покупаемого товара.
  Сопутствующие обязанности поставки сохранять в особых условиях.
  «Ремонтный комплект» и «комплект для ремонта» могут обозначать реальный товар:
