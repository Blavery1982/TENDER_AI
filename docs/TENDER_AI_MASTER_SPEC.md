# TENDER_AI — единая актуальная спецификация

Версия: 1.0

Этот документ — канонический контракт проекта. Production-код, batch/MVP/live
pipeline, Google Sheets и regression-тесты должны реализовывать именно эти
правила. При расхождении сначала исправляется реализация или тест, а не
ослабляется правило ради legacy-совместимости.

## 1. Архитектурный принцип

Уточнение владельца от 16.09.2026: разрешён отдельный контрольный режим
на базе входа Codex CLI (`--product-price-control`), без отдельного AI API.
Кандидат для проверки — GPT-5.6 Luna; эффективность на реальных ТЗ ещё
не подтверждена. Этот режим использует Yandex Search API для ссылок и HTTP/Playwright для карточек, сравнивает
до шести предложений разных продавцов и сохраняет TOP-3. В массовый pipeline
он включается только после контрольной проверки пяти товаров. Описание
детерминированного runtime ниже относится к прежнему массовому контуру.
На контрольный запуск разрешено до 30 платных запросов Yandex Search API,
включая подбор моделей и отложенные задания. Ошибки API останавливают провайдер
без повторов и без перехода на браузерный поиск. Отсутствие credentials
фиксируется до запуска Codex и браузера; текущий backend — macOS Keychain.
При сетевых ошибках выполняется один отложенный повтор после остальных
товаров; CAPTCHA/блокировка требуют ручного восстановления доступа.
Повтор не удаляет результаты первого прохода и не выдаёт их за новые цены.
Полное исходное название сохраняется в «Название позиции (ТЗ)»;
«ВЫБРАННАЯ МОДЕЛЬ» получает только результат основного разбора/подбора.
Повторное угадывание модели при экспорте запрещено.

TENDER_AI — автономная Python-программа. Обычный runtime не требует ChatGPT,
Codex, OpenAI API, LLM или другого генеративного AI. Классификация позиций,
извлечение разрешённых требований, поиск, проверки, расчёты, решение и запись
в Sheets выполняются детерминированным кодом. Модули `ai/` допустимы только
для разработки/отдельной необязательной помощи и не являются обязательным
production-путём.

## 2. Сквозной порядок обработки

Основной обработчик — `pipeline/single_purchase_test.run_check`; live batch
`pipeline/mvp_exact_batch` вызывает ту же цепочку для каждой закупки.

1. карточка ЕАТ, базовые фильтры и `position_kind == goods`;
2. сбор названия товара, всех явно заданных характеристик и указаний модели из карточки, открытого зелёного popup, ТЗ/спецификации, технических разделов контракта/приложений и разрешённого обоснования;
3. установление коммерческого обозначения по контексту поля и наименованию товара; указанная заказчиком модель закрепляется без поиска аналогов;
4. при отсутствии обозначения — поиск моделей только по требованиям заказчика, исключение несоответствий, выбор самой дешёвой полностью подходящей доступной модели;
5. фиксация человеческого полного `ВЫБРАННАЯ МОДЕЛЬ`, отдельный точный поиск одной модели обычной выдачей Яндекса через Playwright;
6. три реальные подтверждённые цены разных идентифицируемых продавцов, с сохранением источников. После трёх подходящих предложений поиск может завершаться;
7. ценовой gate: минимум две полные цены нужного количества `≤ НМЦК × 0,82`, без комиссии, налогов и расходов;
8. только при готовом TOP-3 и интересной цене — выбранные поставщики, antifraud/КАД;
9. только затем юридические/специальные условия контракта, расходы и каноническая итоговая экономика;
10. локальный результат и допустимый экспорт в существующую Google Sheets-схему.

Чтение документов до поиска цены обязательно для сбора товарных требований даже при модели в карточке. Раннее чтение не является юридическим анализом. `.xls` читается локальным xlrd; макросы не запускаются. Нечитаемый/неподдерживаемый документ и неполные характеристики сохраняются как неизвестность, а не успешное чтение.

`MODEL_NOT_RESOLVED` — модель не установлена. `PRICE_SEARCH_FAILED` — необходимые реальные цены не прочитаны/не собраны. `NO_ECONOMIC_SIGNAL` допустим только для определённого товара после реального поиска и отрицательного gate. Неполный TOP-3 не запускает проверки поставщиков. Локальная ошибка не останавливает следующую закупку; системный сбой общего сбора/авторизации не маскируется. «5–7 подач в день» не является целью.

Ни один pipeline не имеет собственного финального decision engine. Если данных
для следующего этапа не хватает, сохраняется явный `unknown`/manual review;
выдуманные цены, наличие, комиссия или успешная проверка запрещены.

## 3. Тип позиции и gate

Каждая позиция получает один из типов: `goods`, `services`, `works`, `mixed`,
`uncertain`. Официальная категория ЕАТ `ТОВАРЫ`/`РАБОТЫ`/`УСЛУГИ` имеет
приоритет над текстовыми эвристиками. Разные определённые типы в закупке дают
`mixed`, а допуск проверяется отдельно по каждой позиции.

EXACT_MODEL и товарный price search разрешены только при
`position_kind == goods`. Для `services`/`works` используется
`NOT_A_GOODS_POSITION`, для `uncertain` — `POSITION_KIND_REVIEW_REQUIRED`.
Модель оборудования, являющегося объектом ремонта/обслуживания, не является
моделью покупаемого товара. Слова «ремонтный комплект» и «комплект для
ремонта» сами по себе не превращают товар в работу, но официальная категория
ЕАТ всегда главнее. Монтаж/сборка сопутствующего товара сохраняются как
особые условия и не меняют тип товара.

## 4. Источники требований и provenance

Явные характеристики из названия, описания и полей карточки собираются вместе с техническими документами. Характеристики берутся только из источников заказчика:

- явных разделов `Спецификация`, `Техническое задание`, описания объекта или
  таблицы характеристик;
- структурированных полей позиции/закупки ЕАТ;
- реально прочитанного popup ЕАТ «Дополнительные характеристики»;
- явно приложенных технических документов;
- разрешённых обоснования цены/КП, если они содержат характеристики.

Ссылки «в соответствии с ООЗ/ТЗ», «см. приложение» не являются характеристиками. Юридические разделы договора, соседние произвольные абзацы и служебные поля
не становятся требованиями автоматически. Для каждого требования сохраняются
источник, документ, страница/поле и фрагмент. Требования разных позиций не
смешиваются. Отрицания (`не требуется монтаж`) исключают обязанность, а не
создают её.

Ценовое evidence хранится отдельно от customer requirement. Модель из
обоснования цены или КП сохраняет `PRICE_JUSTIFICATION`/price evidence и при
отсутствии модели в карточке становится выбранной моделью первичного просчёта. `source_document_type=14` — разрешённый
ценовой источник и не должен отбрасываться как `NOT_FOUND`.

## 5. Модель и режим замены

Система различает `customer_required_model`, модель только из price evidence,
модель из прочего документа и модель, найденную программой. Явно указанная
заказчиком модель без разрешения замены обрабатывается только по
`EXACT_MODEL_ONLY`: аналоги не ищутся и не подставляются.

Если присутствует прямое разрешение «или эквивалент», «эквивалент», «аналог»
или эквивалентная формулировка, в текущей цепочке ищется только исходная модель. Подбор эквивалента — отдельная будущая задача. В результатах сохраняются
`ORIGINAL MODEL` и `EQUIVALENT`; молчаливая замена запрещена.

Для позиции без модели характеристики берутся только из разрешённых источников.
Из полностью соответствующих доступных моделей выбирается самая дешёвая среди
проверенных; глубокий price search выполняется по одной выбранной модели.

## 6. PRICE-FIRST и предложения поставщиков

Для собранного товара закрепляется одна модель: указанная заказчиком либо самая дешёвая полностью соответствующая среди проверенных. Требования не меняются во время price search. Основной запрос — `"<полное коммерческое имя>"`, обычный Яндекс через Playwright. По умолчанию до трёх вариантов запроса и 100 URL; поиск завершается после трёх подходящих реальных предложений или ограничения. Глобальный минимум интернета не заявляется.

HTTP/HTML/JSON-LD/microdata и текущие блоки цены читаются детерминированно, Playwright используется для браузерной выдачи и динамических страниц. Сниппет не подтверждает цену. Старые цены, рассрочка и рекомендации исключаются. Страница должна подтверждать тот же товар/модель и не противоречить существенным требованиям. Неподтверждённые характеристики явно требуют ручной проверки, не дают ложный green.

Подходящее КП должно иметь правильную модель, валидную подтверждённую цену,
возможность поставить нужное количество, непротиворечивое наличие и отсутствие
обязательного antifraud-блокера. Для уверенного расчёта нужны минимум три
разных подходящих supplier offers. Одно или два КП дают `🟡 РУЧНАЯ ПРОВЕРКА`.
Наличие неизвестно — это не подтверждение поставки.

## 7. Полная стоимость КП

Для простой позиции `full_quote_price = unit_price × required_quantity`, если
источник содержит цену единицы. Если источник явно содержит полную стоимость
нужного количества (`full_quote_price`, `quote_total`, `total_price` и т.п.),
она используется без повторного умножения. Двойное умножение запрещено.

Для трёх подходящих КП:

```text
A = (full_quote_1 + full_quote_2 + full_quote_3) / 3
```

`A` — средняя полная стоимость закупки нужного количества. Архитектура должна
поддерживать будущую полную корзину многопозиционной закупки, а не только одну
строку.

## 8. Комиссия ЕАТ

Единственный источник комиссии:

```text
raw.lot.commissionFee → procurement.commission_fee
```

Комиссия не рассчитывается по ставке, НМЦК, цене позиции, цене подачи или
пропорции. `platform_commission()` и ставка 3% не могут быть production
fallback. Отсутствие поля означает `None`/`unknown`, а явный `commissionFee=0`
остаётся подтверждённым нулём. При неизвестной комиссии итоговая экономика
требует ручной проверки.

## 9. Дополнительные расходы

`additional_expenses=0` означает проверенный подтверждённый ноль.
`additional_expenses=None` означает неизвестность и не превращается в 0 ни в
Python, ни в Sheets. Обязанности, которые нужно анализировать: разгрузка,
погрузка, подъём, занос, сборка, монтаж, ПНР, обучение, вывоз упаковки,
пропуска, паспортные/автомобильные данные, режимные объекты, сопровождение и
прочие реальные логистические условия. Типовые оговорки о включённых в цену
транспортных расходах, страховании и налогах не считаются специальными
расходами. Отрицания исключаются. Неизвестную стоимость не заменять нулём.

`special_conditions` строится только после сбора всех документных и позиционных
обязанностей; условия не должны теряться из-за порядка агрегации. Резюме
содержит evidence, но само по себе не меняет сумму расходов.

## 10. Каноническая экономика

```text
bid_price = A × 1.18
total_expenses = A + additional_expenses + procurement.commission_fee
tax_base = max(bid_price - total_expenses, 0)
usn_tax = tax_base × 0.15
net_profit = bid_price - total_expenses - usn_tax
net_profit_percent = net_profit / A × 100
```

УСН — «доходы минус расходы», ставка 15% от положительной налоговой базы,
а не 15% от всей цены подачи. `bid_price > NMCK` — отрицательный критерий при
полном расчёте. Предварительный запас до расходов — только справка и не
заменяет `net_profit_percent`.

## 11. Бизнес-решение

Канонические модули — `calculator/business_decision.py` и
`calculator/result_decision.py`; вход перед записью в Sheets проходит через
`attach_business_decision()`. `calculator/decision.py` может существовать как
legacy/helper, но не формирует production 🟢/🟡/🔴.

`🟢 ПОДАВАТЬСЯ` возможно только одновременно при трёх подходящих КП, полной
экономике, `bid_price <= NMCK`, подтверждённой комиссии, определённых расходах
(включая подтверждённый 0), рассчитанном УСН, `net_profit_percent >= 12%`,
достаточно подтверждённом наличии, отсутствии обязательного antifraud-блокера
и иной неопределённости, способной изменить результат.

`🟡 РУЧНАЯ ПРОВЕРКА` — при 1–2 КП, неизвестной комиссии/расходах, неизвестном
наличии, незавершённом antifraud/КАД, неполной экономике, `uncertain` или иной
обязательной неизвестности. Недостаток данных не превращается в красный.

`🔴 НЕ ПОДАВАТЬСЯ` — только при достаточном полном отрицательном доказательстве:
полная экономика ниже 12%, цена выше НМЦК, невозможность поставки/отсутствие
подходящих вариантов или обязательный блокирующий antifraud-риск.

Решение хранится в JSON и human-readable отчёте. В Sheets в существующей
колонке «Текущий итог просчета и анализа» записываются label и 3–5 коротких
конкретных причин; новые колонки ради причин не создаются.

## 12. Antifraud и КАД

Antifraud запускается после ценового отбора, только для экономически интересных
поставщиков. Ошибка внешней проверки сохраняется явно и не даёт ложный green.
КАД проверяется детерминированным Python/Playwright по однозначному ИНН
актуального продавца. CAPTCHA/защита останавливает попытки и даёт
`KAD_REQUIRES_MANUAL_CHECK`. КАД хранит только минимальные поля: ИНН, дату,
технический статус, `defendant_cases_count`, цвет и короткую причину. Ноль
дел ответчика не создаёт предупреждение; любое положительное число даёт
yellow для ручной проверки. Документы, номера и ссылки дел в production не
хранятся.

## 13. Stale results

Старые `final_economics`, `business_decision`, `economic_precheck` и кеши не
определяют новое решение автоматически. Перед production Sheets-upsert
решение пересчитывается через `attach_business_decision()`. Сохранённая
экономика может быть переиспользована только если совпадают комиссия ЕАТ и её
provenance, количество и A, формула ×1.18, налог и расходы. При сомнении —
пересчёт. Внутренний `decision_version`/schema marker допустим, пользовательскую
колонку Sheets для него создавать нельзя.

## 14. Google Sheets

### Категория закупки

Каждая товарная позиция получает в production-строке колонку `Категория
закупки` с одним из трёх значений: `Закупка по модели`, `Закупка с определением
модели по параметрам` или `Закупка товара без существующей модели`. Сначала
проверяется явное коммерческое обозначение заказчика из разрешённых источников.
Если его нет, модель подбирается по обязательным характеристикам для товаров,
которые на рынке обычно выбираются как конкретные модели. Для массовых и
оптовых товаров без существующей модели применяется третья категория только
при подтверждённом семантическом совпадении со словарём массовых товаров.
Категория 3 останавливает модельный, ценовой, поставщицкий, antifraud-, КАД-,
контрактный и экономический этапы, а в `Текущий итог просчета и анализа`
сохраняется `Алгоритм просчета не доработан`.

Python является единственным decision engine, Sheets отображает его результат.
Используется текущая каноническая схема `google_sheets/kp_schema.py`, включая
блоки КП 1–3, полную среднюю стоимость, количество, цену подачи, НМЦК,
фактическую комиссию, дополнительные расходы, налог, чистую прибыль,
процент, специальные условия и решение. Дублирующие legacy-заголовки и новые
колонки вместо существующих не создаются.

В колонку «Комиссия площадки, ₽» передаётся ровно
`procurement.commission_fee`. `None` остаётся пустым/unknown. Пустая ячейка
дополнительных расходов может получить числовой 0 только по принятому
контракту upsert; существующее число, включая 0, и непустой текст сохраняются.
Расчёты Sheets, если используются, математически совпадают с Python.

## 15. Production entry points и тестирование

`pipeline/orchestrator.py`, `batch_orchestrator.py`, `single_purchase_test.py`,
`live_e2e.py`, `mvp_exact_batch.py`, `priority_production.py`,
`price_search_ready_batch.py` и `second_queue.py` используют общие правила
gate, price-first и decision layer. Локальный контроль одной закупки:

```bash
.venv/bin/python main.py --single-purchase-test <purchase_id>
```

Рабочий журнал «Тесты программы» перед таким запуском очищается только по
телу листа с сохранением заголовков и проверкой режима; другие вкладки не
затрагиваются. Реальную подачу в тендер выполнять нельзя.

Для изменения доменной логики обязательны профильные regression-тесты. Полный
suite запускается только по прямому указанию владельца:

```bash
.venv/bin/python -m unittest discover -s tests -p 'test*.py' -v
```

Обязательные проверки покрывают goods gate, exact/equivalent, источники и
отрицания, PRICE type 14, три full quotes, quantity без двойного умножения,
комиссию/None/0 без fallback, расходы 0/None, ×1.18, NMCK, USN, порог 12%,
stale пересчёт, единый Sheets mapping, special conditions и отсутствие
production-зависимости от legacy decision engine.

### История triage legacy-suite

Исходный контрольный прогон насчитывал 878 тестов: 829 успешных, 43 падения и
6 ошибок. Из 49 исходных проблем 3 относились к production (агрегация
`special_conditions` и потеря `source_document_type=14`), 44 — к устаревшим
