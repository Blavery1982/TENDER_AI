# TENDER_AI

Каноническая спецификация проекта: [docs/TENDER_AI_MASTER_SPEC.md](docs/TENDER_AI_MASTER_SPEC.md).
Она является единым источником правил для production-кода, pipeline, Google Sheets
и тестов; README содержит только краткую навигацию и рабочие команды.

## Контрольный просчёт и локальные проверки

```bash
.venv/bin/python main.py --single-purchase-test bc152af1-ef03-4f39-a194-a01b798589e6
```

Контроль одной закупки записывает LIVE-этапы на лист «Тесты программы»
существующей Google-таблицы и подтверждает запись чтением обратно.
Локальные результаты находятся в `data/test_runs/`.

До определения модели и поиска цен детерминированный классификатор определяет
тип каждой позиции. Категория ЕАТ `ТОВАРЫ / РАБОТЫ / УСЛУГИ` имеет приоритет.
Только `goods` допускается к товарному поиску; `works/services` блокируются,
`uncertain` требует ручной проверки, разные определённые типы дают `mixed`.
Модель объекта ремонта/обслуживания не является моделью закупаемого товара.
Сопутствующий монтаж/сборка товара сохраняется в особых условиях.

Для каждой товарной позиции сначала собираются название, все явно заданные требования и обозначение модели из карточки/зелёного popup, ТЗ/спецификации и технических разделов контракта. Ссылки «в соответствии с ООЗ/ТЗ» не являются характеристиками. Поддерживается локальное чтение обычного `.xls`.

Указанная заказчиком модель закрепляется полным коммерческим именем, без аналогов. При отсутствии модели выбирается самая дешёвая полностью соответствующая доступная модель по требованиям заказчика. Затем выполняется отдельный точный поиск в Яндексе через Playwright: три подтверждённые цены разных продавцов → gate двух полных цен ≤ НМЦК × 0,82 → только выбранные поставщики/antifraud/КАД → юридические условия контракта → расходы → каноническая экономика. До цены документы читаются только для товарных сведений; юридический анализ отложен. Основной обработчик `pipeline/single_purchase_test.py` используется live batch.

По умолчанию до трёх поисковых запросов и 100 URL; после трёх подходящих предложений поиск может завершаться. Цены подтверждаются на страницах, старые цены/рекомендации исключаются. Модель не установлена → `MODEL_NOT_RESOLVED`; нужные цены не получены → `PRICE_SEARCH_FAILED`; `NO_ECONOMIC_SIGNAL` — только после реальных цен и отрицательного gate. Неизвестные характеристики сохраняются явно и требуют ручной проверки.

Комиссия берётся только из `raw.lot.commissionFee` → `procurement.commission_fee`; отсутствующая комиссия/расходы не превращаются в ноль. Формула экономики и схема Google Sheets сохранены.

Полный regression suite разрешён только по прямому указанию владельца,
в том числе перед live-run. Механизм сохранён: устаревший флаг
`--tests-google-sheets` теперь создаёт только локальный отчёт UNIT.
Отдельные UNIT-тесты в рабочую Google-таблицу не выгружаются.
Для локальных изменений выбирать минимальные профильные проверки (5–30),
не запускать большие соседние наборы и не повторять проверки без необходимости.

Локальный проект на Python для будущей работы с тендерами.

## Структура проекта

- `app/` — основная логика приложения и его интерфейс.
- `eat/` — будущая работа с ЕАТ.
- `filters/` — правила отбора и фильтрации тендеров.
- `google_sheets/` — будущая интеграция с Google Таблицами.
- `suppliers/` — данные и логика работы с поставщиками.
- `calculator/` — расчёты стоимости и других показателей.
- `security/` — функции безопасной работы с данными.
- `reports/` — создание отчётов.
- `data/` — локальные рабочие данные.
- `data/tenders/<tender_number>/` — архив новой закупки по её номеру ЕАТ: исходные документы,
  `tender.json`, `document_extraction.json` и `brand_audit.json`.
- `logs/` — технические журналы работы программы.
- `config/` — настройки приложения без секретных данных.
- `tests/` — автоматические проверки программы.
- `main.py` — точка запуска программы.
- `requirements.txt` — список необходимых библиотек Python (пока пуст).
- `.env.example` — пример будущих переменных окружения без секретов.

Настоящие пароли, токены и ключи нельзя записывать в код. В будущем они будут храниться отдельно в локальном файле `.env`, который исключён из Git.

## Учётные данные магазинов

Разрешённый сайт сейчас — `onlinetrade.ru`. Список содержит только домены;
логины и пароли хранятся отдельно в macOS Keychain (`TENDER_AI_SHOPS`),
не в `.env`, JSON или архиве закупки. Вводить данные вручную в локальном терминале:

```bash
.venv/bin/python -m security.shop_credentials setup onlinetrade.ru
.venv/bin/python -m security.shop_credentials list
```

Логин и пароль вводятся скрыто. `list` показывает только сайт и статус настройки.
Для программы доступны `get_shop_credentials(url)` и `authenticate_shop(page)`
из `security.shop_credentials` и `model_search.shop_auth`. Вход выполняется только
в однозначную штатную HTTPS POST-форму разрешённого сайта, без повторов.
CAPTCHA и одноразовые коды требуют ручного прохождения; пароль не обходит CAPTCHA.
Исследовательский `browser_research.py` поддерживает команду `{"action":"login"}`
для уже открытой формы. Автопереход к форме входа конкретного магазина не реализован:
если форма не обнаружена, возвращается `manual_login`. Реальный вход нужно проверить
после настройки данных и прохождения CAPTCHA; уже запущенный процесс скрипта нужно
перезапустить, чтобы он прочитал новый обработчик (не закрывать CAPTCHA до прохождения).
Новые сайты добавлять в разрешённый список только по указанию владельца.

## Архив документов и проверка марок

Новая загрузка карточки через `eat.single_purchase` сохраняет все документы в отдельную папку
`data/tenders/<tender_number>/`, где `tender_number` — номер закупки ЕАТ (`tradeNumber`).
UUID остаётся в `tender.json` и ссылках API. Существующие папки сохраняют прежние имена:
повторная загрузка уже сохранённой закупки использует её старую папку.
Без номера ЕАТ новый архив не создаётся. Старые документы из `data/contracts/`
перенесены в новый архив и удалены.

Одноразовая миграция уже скачанных документов выполняется командой:

```bash
.venv/bin/python -m documents.migrate_tender_archive
```

Проверка локального архива на марки и товарные знаки:

```bash
.venv/bin/python main.py --audit-tender-archive
```

Создание паспорта состава файлов для каждого тендера:

```bash
.venv/bin/python main.py --build-tender-passports
```

В каждой папке появляется структурированный `passport.md` — основной паспорт тендера
для чтения и извлечения информации.

Результаты находятся в `data/tenders/_brand_lists/`:

- `brands_found.json` — подтверждённая марка найдена, с документом, страницей и фрагментом;
- `brands_not_found.json` — все документы прочитаны, совпадений нет;
- `review_required.json` — неполный архив, ошибка OCR или неоднозначный кандидат.

## Финальные КП в основной Google Sheets

Детерминированное бизнес-решение находится в `calculator/business_decision.py`;
`calculator/result_decision.py` адаптирует сохранённый EXACT_MODEL просчёт.
Объект `business_decision` содержит статус, причины, бизнес-порог чистой прибыли
12%, число уникальных подходящих доменов и лучший
подходящий вариант в исходном порядке. Поиск не запускается; при наличии
сохранённых трёх КП и входов новой формулы выполняется только
локальный детерминированный расчёт, без поиска и внешних проверок.
Решение сохраняется в JSON и начале локального Markdown-отчёта. В основной
Google Sheets статус и причины записываются в существующую колонку
«Текущий итог просчета и анализа»; в контрольном журнале — отдельным этапом
«Бизнес-решение». Обычный сбор сохраняет готовое решение; новый просчёт заменяет его.

Итоговая рентабельность имеет приоритет над предварительным запасом.
Предварительный запас хранится отдельно и служит только промежуточной справкой:
сам по себе он не разрешает зелёный статус и не доказывает необходимость отказа.
Для старых результатов запас корзины относится только к совпадающим поставщику
и цене единственной позиции. Показатель не распространяется на остальные КП.

Цена подачи для новой формулы равна `A × 1,18`, где `A` — средняя цена трёх
подходящих КП. В расходы входят `A`, дополнительные расходы и комиссия ЕАТ;
УСН «доходы минус расходы» считается как 15% положительной налоговой базы.
Чистая прибыль должна быть не ниже 12% от `A`, а цена подачи — не выше НМЦК.
Этот расчёт выполняется функцией `calculate_bid_economics`; неполные входы
не подменяются предварительным запасом.

🟢 требует завершённого просчёта, проходной итоговой рентабельности, минимум трёх
подходящих доменов, подтверждённого наличия у важных поставщиков, чистого antifraud
и учтённых обязательных расходов. 🟡 применяется к неполным данным, недостаточному
резерву, неподтверждённому наличию, предупреждениям и неучтённым особым условиям.
🔴 требует достаточного отрицательного доказательства: полной непроходной экономики,
завершённого просчёта без вариантов либо подтверждённой невозможности поставки.
Принятое владельцем правило «неполная экономика → ручная проверка» является
основным; `rule_candidates` для него пуст. `decision_version=2`.

Сохранённая итоговая рентабельность читается из `final_economics`/`economics`
(`net_profit_percent`, либо совместимое старое `profitability_percent`) либо
итоговых полей предложения. Полнота подтверждается
`economics_complete=true`/`complete=true` и `mandatory_expenses_included=true`,
либо полным денежным снимком существующей `calculate_economics` с комиссией и
расходами. Явная незавершённость и неизвестные обязательные расходы имеют приоритет
над положительными флагами. Общая экономика всей закупки не присваивается каждому
предложению: для переноса требуется совпадение корзины или закупочной стоимости
и количества единственной позиции. Без подтверждения данных результат остаётся 🟡.

Причины сохраняются в пяти пунктах: цена, итоговая экономика, возможность поставки,
проверка важных поставщиков, число подходящих доменов. Для нескольких позиций
требуется также завершённая общая корзина; итог содержит `position_decisions`.

`publish_business_decision(payload)` позволяет записать только итог сохранённого
просчёта: сверяет ID/позицию, цены, товарные ссылки, поставщиков и antifraud
текущих КП, затем пишет одну ячейку RAW и проверяет чтением обратно.
При несовпадении старое решение не переносится в изменённые КП.

`google_sheets/production_upsert.py` записывает финальные предложения в
существующие блоки КП1–КП3. Каждый блок содержит поставщика, цену за единицу,
отдельную рентабельность, прямую товарную ссылку, ссылку на реально полученный
счёт (или пустое поле) и краткий antifraud. `google_sheets/kp_schema.py`
переиспользует старые колонки поставщиков, перемещая целые колонки штатным
Sheets API; новые добавляются только при отсутствии соответствующих старых.

Поток `select_verified_top3()` исключает красных кандидатов и проверяет следующих.
Подтверждённое наличие и «под заказ» имеют приоритет; неизвестное наличие
используется для оставшихся мест только при отсутствии трёх надёжных
актуальных карточек во всём пуле, до экономического допуска. Итоговые КП
сортируются по цене.
Mapping проверяет свидетельства текущего поиска (`price_run_id`, `checked_at`,
подтверждение страницы, модели и цены). При повторной записи КП заменяется
целиком; отсутствующие предложения очищаются.

Рентабельность каждого КП в существующем блоке расчётов не менялась. Новая
формула цены подачи применяется только в слое бизнес-решения: резерв между
НМЦК и закупочной ценой остаётся промежуточной справкой и не заменяет чистую
прибыль. Если расходы или другие обязательные данные неизвестны,
рентабельность остаётся пустой. Публичная цена не становится подтверждённой
закупочной ценой, расчёт остаётся предварительным.

`Дополнительные расходы, ₽`: production-upsert отдельно проверяет ячейку
и записывает числовой `0`, если она пустая. Существующее число, включая `0`,
сохраняется без перезаписи. Непустой текст автоматически не заменяется.
Обычный сбор сохраняет поле. Существующая формула использует числовое значение
из Sheets. Анализ не оценивает денежные расходы и не создаёт
дополнительного запрета расчёта по тексту контракта.

`audit.contract_analysis` передаёт короткое резюме отдельных обязанностей
в `РЕЗУЛЬТАТ АНАЛИЗА КОНТРАКТА`: разгрузка, подъём, сборка, пропуска и другие
особые требования. Стандартная оговорка о включённых в цену транспортных
расходах, страховании, налогах и сборах, а также обычная поставка игнорируются.
При отсутствии отдельных требований: `Нет специальных условий`.

Профильная проверка без сети и выгрузки UNIT:
`.venv/bin/python -m unittest tests.test_kp_mapping tests.test_google_sheets_formulas`.
